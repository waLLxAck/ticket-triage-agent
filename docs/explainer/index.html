ticket-triage-agent
Learning project · how it works, step by step

One support ticket, from inbox to decision

An LLM agent reads a customer support ticket, works out what it is about, drafts a reply from the help centre, and then plain code decides whether that reply can go out on its own or needs a person. All seven phases are built. The agent runs on AWS behind a queue, every pull request is scored by an eval gate, and two client change requests have gone through it. This page takes it apart one phase at a time, with the real numbers, then runs the whole thing end to end.

Acme Pay is fictional. This is a demo that simulates a Lead AI Engineer contract at a UK fintech. There are no real customers, cards or accounts; every example ticket was written for testing.

core idea
The model proposes, code decides.
The LLM fills in typed forms. Deterministic rules read those forms and choose what reaches a customer.

Phase 1

The agent

What it is

A LangGraph state machine with four steps: classify the ticket, retrieve help-centre articles, draft a reply from them, and run the policy gate. It runs locally with uv run triage "…" and returns a TriageResult.

Why a client needs it

A fintech can't send a reply that invents a fee or promises a refund. Each step here exists to make the agent's output checkable: typed fields, answers grounded in the client's own articles, and a rulebook a compliance officer can read.

How it connects

It uses the Bedrock access from Phase 0. Phase 2 adds two nodes in front of classify, Phase 3 measures it, Phase 4 runs this same graph inside a Lambda.

State, nodes, edges
State is a typed dict. Each node is a plain function that reads the state and returns only the keys it changed. Edges say what runs next.
Conditional edge
after_classify reads the state: an unknown ticket jumps straight to policy. That saves an LLM call and removes a chance to hallucinate.
Structured output
The model fills in a Pydantic model through Bedrock tool calling, so the code gets typed fields instead of prose to parse.
Retrieval (the R in RAG)
The reply may only use facts from the articles that were retrieved. Here retrieval is a keyword scorer with a same-category boost. Phase 3 added simple plural folding, so "payments" matches "payment".
Deterministic policy gate
Rules in plain Python decide auto_resolve or escalate. Phase 1 had five; there are nine now, each added after a failure the evals or production found. The model's opinion is an input, not the decision.
Provider seam and fake LLM
The graph only knows the TriageLLM protocol. Unit tests pass a FakeLLM, so they're free, instant and don't touch AWS.

A weakness found here, measured and fixed in Phase 3. In the first live run the fraud ticket retrieved kb-003, kb-004 and kb-005 and missed kb-007 ("Lost or stolen card", which says to report fraud). With the Phase 1 code no article had the category fraud_report, so the +3 boost never fired for a fraud ticket, and the ticket shared at most one word with any article, so ties in file order decided the top 3. The eval suite turned this into a number (retrieval hit rate 97%, fraud-01 missed kb-007). The fix was two lines: kb-007 is now also tagged fraud_report, and plurals fold. The hit rate went to 100%.

The scores here are computed in your browser with the same tokeniser, stopwords, plural folding and +3 boost as knowledge.search, on the short sentence shown. The logged live run used the ticket exactly as typed then, which may have had a few more words.

Phase 2

Guardrails

What it is

Two new nodes before classify. redact masks personal data with regexes before any LLM call. guard looks for prompt injection with patterns and a cheap LLM check, and sends a flagged ticket straight to policy. After drafting, an output check holds any reply that leaks personal data or promises something only a human may promise. Phase 3 and CR-001 later taught it two more things: unsafe advice and links.

Why a client needs it

UK GDPR's data-minimisation principle: don't send a third party data it doesn't need. The model doesn't need the card number to see a double charge. And a reply saying "your refund has been approved" is exactly the kind of mistake that ends up at the Financial Ombudsman.

How it connects

Phase 1's nodes are untouched. The graph gains START → redact → guard, a second conditional edge, and the policy gate gains two inputs: injection_reasons and output_problems.

Redaction order matters
IBAN runs first, because an IBAN contains digit runs that would otherwise look like an account number. Then card, email, UK mobile, sort code, 8-digit account number.
Luhn check
Card numbers end in a check digit. A 16-digit order reference that fails the check is left alone, so the agent doesn't over-redact.
Defence in depth
Regex heuristics are free and catch obvious attacks; an LLM judge (InjectionCheck) catches polite ones the patterns miss. Either one flags the ticket.
Fail closed
A flagged ticket is never classified or drafted. The policy returns escalate with "possible prompt injection", and the result records injection_flagged=true.

Phase 3

Evals and Langfuse

What it is

A file of labelled tickets, evals/dataset.jsonl: 50 at the first baseline, 55 now, including 7 red-team attacks and 3 that only look like attacks. evals/run.py sends every one through the real agent on Nova Lite, scores the results against the bars in thresholds.toml (12 then, 14 now) and writes a pass/fail report. Langfuse keeps a trace of every run and stores each full eval as an experiment.

Why a client needs it

Phases 1 and 2 looked right on a handful of tickets. The first eval run found two incidents that no manual test had shown: the agent told a phishing victim to follow the link, and it made up a fee policy. Without evals, "I improved the prompt" is an opinion. With them it's a number.

How it connects

It runs the Phase 2 graph unchanged. Phase 5 runs it on every pull request and posts the report as a comment. In Phase 6 the thresholds are the contract's acceptance criteria, and the gate failed three runs on two bad changes.

Labels describe the business
Each case says what a good support lead would want: acceptable categories, auto-resolve or escalate, which article should ground the reply, which PII must go, and whether it's an attack. Labels copied from what the code currently does prove nothing.
Safety, quality and limits
Safety bars are 100%: one fraud ticket auto-resolved is an incident, not a statistic. Quality bars are the service levels agreed with the client. Limits are maximums: latency, cost, false alarms.
Automation pulls against safety
Escalating everything scores 100% on safety and 0% on automation. The job is to raise automation_rate without ever dropping a safety bar, and the gate makes that trade-off visible.
Don't overfit to the failure
For each bug class found, new cases were added (fraud-06 email phishing, fraud-07 a WhatsApp PIN request, fees-06), not just a re-run of the ticket that failed.
Trace, span, generation
A trace is one run. It holds a span per graph node, and each Bedrock call inside a node is a generation, with its prompt, output, token counts and latency.
Datasets and experiments
run.py upserts the cases as the Langfuse dataset acme-triage and runs the agent as an experiment named after the prompt version, such as v6-20261127-171956. Two runs can be compared ticket by ticket.

Every value comes from a recorded report: the v2 baseline and v4 columns of docs/guide/03, evals/history/v4.md, and the gate comment on PR #3. The baseline report itself isn't kept in the repo, so only the tickets the guide names are marked for v2.

The quota, a production lesson learned in a test run. Running tickets four at a time produced ThrottlingException errors. This account's Bedrock quota is 20 requests a minute for Nova Lite (AWS's default is 200), and a ticket makes 3 calls, so about 6 tickets a minute. A shared RateLimiter now paces calls to 18 a minute, leaving headroom, and completion_rate joined the safety bars, so a run with errored tickets can never pass on the tickets that happened to finish. Latency is reported without the time a ticket spent queued for a slot (queued_ms is kept separately). Phase 4 found that this first limiter was too strict.

The tree shape, node names, masking result, run names and retrieved articles are real. Token counts and timings are recorded per generation in Langfuse but aren't kept in the repo, so they aren't shown here. The three generations are labelled by the structured-output model each call fills in.

Phase 4

AWS, defined in Terraform

What it is

A Lambda Function URL in front of triage-api (FastAPI through Mangum), which checks the API key, redacts, saves the ticket and enqueues it. SQS triage-tickets feeds triage-worker, which runs the graph and writes the result to DynamoDB. A dead-letter queue, two alarms, a $1 budget and SSM secrets complete it. Every resource is in infra/app/*.tf.

Why a client needs it

A laptop CLI isn't a service. The queue absorbs bursts and retries failures, so nothing is lost silently. One role per function limits the damage if code goes wrong. Terraform makes every change reviewable in a pull request, repeatable for a staging copy, and removable with one command.

How it connects

The worker calls the same triage() as the CLI and the evals. Phase 5 runs terraform apply from GitHub Actions. The live smoke test found two problems the evals hadn't: a slow rate limiter and a made-up link, which became Phase 6's first change request.

Bootstrap, then app
The state bucket and the CI roles must exist before CI can deploy, and a bucket can't hold the state of the config that creates it. So infra/bootstrap runs once from the laptop; infra/app is deployed by CI.
Shared, locked state
Terraform's state lives in a private, encrypted, versioned S3 bucket, so the laptop and CI share one copy. use_lockfile = true stops two applies colliding.
One zip, no Docker
scripts/build_lambda.py downloads Linux wheels on Windows with uv pip install --python-platform x86_64-manylinux_2_28. At 48.7 MB it's just under the 50 MB direct-upload limit, so it goes through S3.
Cold start: 3.5 s
The first request to a new Lambda instance loads Python and every library, and LangChain is heavy. Warm requests skip it. The fixes all cost something: smaller dependencies, more memory, or provisioned concurrency, which isn't free.
Queue, retries, dead letters
A failed message reappears after the visibility timeout (12 minutes, 6× the worker's 120 s timeout). After 3 receives it moves to triage-tickets-dlq and an alarm emails. ReportBatchItemFailures retries only the failed messages.
Secrets in SSM
The API key and the Langfuse keys are SecureString parameters, free on the standard tier. The Lambda environment holds only their names; settings.load() fetches the values at cold start, and Terraform marks them sensitive.
DynamoDB inside the free tier
Provisioned at 5 read and 5 write capacity units, inside the always-free 25/25. On-demand would be simpler but bills per request. The review queue uses a Scan, fine at demo volume.
Operations
CloudWatch logs kept 7 days. Alarms on "DLQ not empty" and "worker errors" email through SNS. A $1 monthly budget emails at 50% actual and 100% forecast.

The quota, the 6.7 s spacing, the 19.5 s and 1.9 s totals, the 2 × 9 split and the 22-calls-in-54-seconds point are real. The bars run the same algorithms as RateLimiter, with the 1.9 s of model time split evenly across the three calls for drawing.

Two findings from production that the evals didn't catch. First, a single ticket took 19.5 s in Lambda for 1.9 s of model work, because the first limiter spaced every call 6.7 s apart. It became a token bucket. Second, the very first live reply ended with [kb-002](https://example.com/kb-002): the model had made up a URL. In a bank's message a link is the classic phishing pattern, and no eval metric looked at links. That became CR-001.

Phase 5

CI/CD with GitHub Actions

What it is

One workflow, .github/workflows/ci.yml. On every pull request: ruff, a format check and the unit tests, then the eval gate against the real model, which posts its report on the PR. On main: a deploy job in the production environment that builds the zip, runs terraform apply and smoke-tests the live URL.

Why a client needs it

Nobody deploys from a laptop, and nobody merges a prompt change without numbers. Branch protection makes the gate binding rather than advisory. AWS access uses OIDC, so the repo holds no AWS key that could leak.

How it connects

The eval job runs Phase 3's suite; the deploy job runs Phase 4's Terraform. In Phase 6 the gate's PR comments are where each change request was accepted or rejected.

OIDC instead of keys
GitHub signs a short-lived token that says which repo and context is running. AWS STS checks the signature and the claims, then hands out credentials that last an hour.
Two roles, two scopes
triage-gha-eval trusts PRs and branches and may only invoke one model: a malicious PR can spend about a penny. triage-gha-deploy trusts only environment:production, which GitHub allows only from main.
Immutable subject
GitHub now signs the owner and repo IDs into the subject. If the repo were deleted and someone recreated one with the same name, it wouldn't inherit the trust.
Forks get nothing
A fork's PR gets no repository secrets and can't be granted id-token: write, so it can't ask for a token at all. The workflow must never switch to pull_request_target.
One eval at a time
Evals share one Bedrock quota, so concurrency: eval queues them, with queue: max so a waiting PR's run isn't dropped.
Stale-commit guard
Concurrency runs one deploy at a time but doesn't guarantee push order. The deploy's first step skips itself if main has already moved on to a newer commit.

Phase 6

A simulated contract

What it is

Work on the finished system the way a forward-deployed engineer does: under a statement of work, with a defect report (CR-001), a client change request (CR-002), code review, and a runbook for handover. Every change had to get through the eval gate. All of it happened on GitHub on 27 November 2026.

Why a client needs it

Clients pay for changes that don't break what already works, and for evidence. Here the gate failed three runs, on two changes that passed every unit test, and each failure named the metric and the tickets.

How it connects

Everything before it is the machinery; this phase uses it. The paperwork is in docs/contract/: SOW.md, CR-001-made-up-links.md, CR-002-lost-card-fast-path.md, RUNBOOK.md.

Statement of workSOW.md · fictional client

Problem. Support receives about 12,000 tickets a month. Most are routine and answered by copying help-centre text, while urgent tickets (fraud, scams, locked-out customers) wait in the same queue.

Outcome. Auto-resolve routine tickets with grounded replies; route fraud, scams, complaints, attacks and anything uncertain to a human every time; never send personal data where it isn't needed or promise refunds; be measured continuously and blocked from release if it regresses.

Deliverables. D1 agent · D2 guardrails · D3 eval set, gate and tracing · D4 AWS in Terraform · D5 CI/CD with OIDC · D6 runbook.

Term: 6 weeks, fixed scope, outcome-based. Out of scope: helpdesk integration, sending email, identity checks, any action on an account.

CR-001 · made-up links (defect)found by the smoke test

The first live reply ended with You can find more details in our article [kb-002](https://example.com/kb-002). The gate checked which article a reply cited, not what the reply text contained.

Change: the output guard flags any URL, www. address or internal ID; prompt v5 forbids links and IDs; two new metrics, clean_draft_rate (does the prompt produce clean drafts? ≥ 95%) and unsafe_auto_replies (did the guard let anything out? = 0).

The gate failed it. The guard flagged "Please do not click the link", the right advice, because the regex ignored negation. And the made-up fee policy came back under the new prompt.

Prompt v6: every fact needs a supporting_quotes entry copied from an article, and knowledge.quote_is_verbatim checks it in code. The check became negation-aware. Clean drafts 100%; automation fell from 93% to 81.5%, because some correct answers now escalate when the quote isn't word-perfect.

CR-002 · lost-card fast path (change)raised by the Head of Support

"When a customer says they've lost their card, they wait in the human queue because the agent marks it high urgency. Send them the freeze instructions straight away. If there are payments they don't recognise, that's still fraud."

Acceptance tests first: card-03, new card-08 and card-09 must auto-resolve citing kb-007; fraud-04, urgent-01, urgent-02 and angry-01 must still escalate.

What this phase teaches that the others couldn't

  1. A metric only protects you from what it measures.CR-001's made-up link passed every gate because no metric looked at links. After a production finding, first add the check that would have caught it, then fix it.
  2. Guards can be wrong too.The output guard blocked correct safety advice. clean_draft_rate and unsafe_auto_replies measure the prompt and the guard separately, so a broken guard shows up as a number.
  3. Prompts drift, structure holds.The made-up fee was fixed by a prompt in v3 and came back in v5 after an unrelated edit. A quote that code checks is a structural fix.
  4. Unit tests and evals catch different bugs.CR-002 attempt 1 passed all 43 unit tests and was still wrong. Unit tests prove the code does what you wrote; evals prove what you wrote is what the client needs.
  5. Code review is part of the deliverable.An IAM escalation path or a lost human decision isn't a nit. It's what a client's security team would raise in week two.
  6. Least privilege costs some iteration.The deploy role took two failed runs to get right. Each failure named the exact missing action, and the role holds exactly what the deploy needs.

See it all together

Send a ticket through the whole system

Pick a ticket. It travels the deployed path, from the API through the queue and the worker's graph to DynamoDB, and the decision trace builds line by line exactly as graph.py writes it. The redaction, injection patterns, scam signals, retrieval, output check, quote check and policy run in your browser, copied from the repo's code.

What's real here. The coffee, fraud and weather tickets come from the first live run. The lost-card, phishing and pii-01 tickets are eval cases, and the action shown matches their result in the final CI gate (card-03 auto-resolved, fraud-05 escalated, pii-01 escalated for its quote). The injection ticket is an example of what the guard code does. Every verdict, trace line and retrieved article is computed by the copied code from the inputs; the urgency and confidence values, reasoning sentences, quotes and reply text are illustrative, as is the guard's LLM reason. Token counts, cost and latency are left out of the result here.
